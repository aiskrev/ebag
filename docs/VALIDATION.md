# Проверки

## 04.11.2026

Първа проверка на реалния Docker stack (Docker 29.9.2, Windows 11, WSL2).

### Успешни

- 95 unittest теста в python:3.12-slim. Резултат: test-results.txt.
- `docker compose build` и `up`: контейнерът стартира с read-only файлова
  система, `cap_drop: ALL`, non-root потребител и named volume.
- `health`, `report`, `notifications`, `smtp-test`, `backup` работят до scheduler-а.
  Без SMTP настройки `smtp-test` завършва с ясна грешка.
- Втори `ebag schedule` се отказва. Рестартът освобождава lock-овете.
- Реален scheduler процес срещу затворената защита, с отделна база: slot
  `blocked_review`, причина в DB, 0 наблюдения, 0 страници с продукти.
- Реален live crawl в контейнера с `ebag run --send` срещу release `2d86517`:
  status=success, 850 продукта, 50 страници, 256.5 s, 0 parser грешки, 0 email-а.
  Frontier пази 17 страници за следващия обход. SQLite integrity_check: ok.
  Втори обход същия ден: success, 987 продукта, 0 parser грешки.
- Схема спрямо fixtures от 24.10: няма премахнати или добавени полета, включително
  в EUR цените. Сравнението е с 20-те fixture продукта.
- Единични цени: 845 от 850 имат стойност. 5 перилни препарата нямат физическо
  количество и правилно остават null. Проверените примери са смислени.
- Класификация: 740 IGNORE, 110 WATCH, 0 BUY, всички LOW увереност. Това е
  очакваното поведение без предишна история.
- По време на crawl втори `ebag run` се отказва. След него `health` е зелен.
- Реален email: smtp.abv.bg:465 прие тестово писмо (TLS с проверен сертификат, вход)
  и собственикът потвърди, че то пристигна в aiskrev@abv.bg.
- Целият pipeline след crawl-а (`cli.run`, оценка, `deliver`, SMTP) срещу локален
  STARTTLS сървър: AUTH и MAIL само след TLS, multipart писмо, кирилица в темата,
  без дублиране. Недоверен сертификат се отказва и паролата не стига до сървъра.

### Открити при първото пускане и поправени

- Scheduler-ът държеше lock постоянно: `smtp-test`, `report` и `run` спираха с
  „Another instance holds database lock“. Документираното възстановяване с
  `ebag run --send` не беше възможно при работещ контейнер.
- Първият неуспех изразходваше деня, дори при временна мрежова грешка.
- Логовете на scheduler-а стояха в буфера (липсваше PYTHONUNBUFFERED).
- Работещ crawl изглеждаше като срив в health.
- Email грешка маркираше crawl-а failed и губеше frontier.
- Един лош продукт отменяше всички наблюдения за деня.
- Release проверката четеше страница от 1-часовия кеш.

### Непроверено

- Реалното тестово писмо през smtp.abv.bg:465 е още единствената реална доставка;
  писмо с истинска BUY оферта още не е изпращано, защото няма история.
- Дневен цикъл в 08:00 и многодневна работа: не са наблюдавани.
- Автоматично дневно резюме: проверено върху реалните данни с `ebag summary` и с
  тестове, но още не е пращано от обход.
- Обновяване на познати продукти през `/products/{id}/json`: първият обход няма
  познати продукти, затова този път още не е минал с реални данни.
- Автоматичният дневен backup: минава само при scheduled обход, който още не е
  наблюдаван в контейнера. Покрит е с тест.
- Рестарт на Windows: не е изпробван. Docker Desktop е изключен от автоматичния
  старт. Контейнерът е с `restart: unless-stopped` и работи от постоянна папка;
  след преместването `health` е зелен и 850-те наблюдения са налични.
